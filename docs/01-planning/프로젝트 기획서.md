## 2. 프로젝트 배경

### 작성 목적

서비스 운영 환경에서는 단순히 애플리케이션을 정상적으로 배포하는 것뿐만 아니라, 장애를 빠르게 감지하고 복구하여 서비스 중단 시간을 최소화하는 것이 중요하다.

기존의 수동 장애 대응 방식은 운영자가 장애를 직접 인지하고 원인을 확인한 뒤 복구 작업을 수행해야 하므로, 장애 탐지와 복구까지 일정 시간이 소요된다.

이에 Kubernetes의 Self-Healing 기능과 Prometheus 기반 모니터링을 활용하여 장애 탐지 및 복구 과정을 자동화하고, 수동 대응 방식과 비교하여 실제로 장애 복구 시간이 얼마나 개선되는지 검증하고자 한다.

---

## 3. 문제 정의

> 서비스 장애 발생 시 사람의 수동 대응에 의존하면 장애 탐지와 복구까지 시간이 증가하고, 그동안 사용자 요청 실패 및 서비스 가용성 저하가 발생할 수 있다.
> 

### 세부 문제

| 문제 | 설명 |
| --- | --- |
| 장애 탐지 지연 | 운영자가 직접 확인하기 전까지 장애 인지가 늦어질 수 있음 |
| 수동 복구 의존 | Pod 재시작, 상태 확인 등을 사람이 직접 수행 |
| 장애 대응 일관성 부족 | 운영자마다 대응 방식과 시간이 달라질 수 있음 |
| 배포 장애 | 잘못된 버전 배포 시 서비스 오류가 장시간 지속될 수 있음 |
| 모니터링 부족 | 장애 발생 시 원인을 빠르게 파악하기 어려움 |

## 6. 장애 시나리오

### Scenario 01 — Pod Failure

**목적**

Kubernetes Self-Healing 효과 검증

**장애 방식**

```
kubectl delete pod <pod-name>
```

**확인 항목**

- 장애 감지 시간
- 신규 Pod 생성 시간
- Ready 상태 복귀 시간
- Error Rate
- P95 Latency

### Scenario 02 — Resource Exhaustion

**목적**

CPU / Memory 부하 상황에서 서비스 안정성 검증

**확인 항목**

- CPU
- Memory
- Pod 상태
- HPA
- Error Rate
- P95
- Recovery Time

### Scenario 03 — Deployment Failure

**목적**

잘못된 버전 배포 시 장애 탐지 및 Rollback 검증

**확인 항목**

- 배포 실패 감지 시간
- Error Rate
- Rollback 시간
- 정상 서비스 복귀 시간

## 7. 측정 지표

| 지표 | 의미 |
| --- | --- |
| MTTD | Mean Time To Detect |
| MTTR | Mean Time To Recovery |
| P95 Latency | 전체 요청의 95%가 완료되는 응답시간 |
| Error Rate | 실패 요청 비율 |
| Availability | 서비스 가용률 |
| Recovery Time | 장애 발생 후 정상 상태 복귀까지 시간 |
| Pod Restart | Pod 재시작 횟수 |
| Pod Ready Time | 신규 Pod Ready까지 걸린 시간 |

---

## 8. 성공 기준

- 자동 복구 환경의 MTTR이 수동 대응 환경보다 짧아야 한다.
- Pod 장애 발생 후 Kubernetes가 새로운 Pod를 자동 생성해야 한다.
- 장애 발생 후 서비스가 정상 상태로 복귀해야 한다.
- 장애 구간의 Error Rate와 P95 변화가 측정 가능해야 한다.
- Prometheus/Grafana에서 장애 발생과 복구 과정을 확인할 수 있어야 한다.
- 잘못된 배포 발생 시 정상 버전으로 복구할 수 있어야 한다.
- 모든 테스트는 동일한 조건에서 반복 가능해야 한다.
