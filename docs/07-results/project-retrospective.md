## 1. 자동 복구 효과

ReplicaSet이 Pod 장애 발생 후 원하는 상태를 자동으로 복원하는 것을 확인했다.

측정한 Pod Ready 도달 시간은 수동 평균 19.101초, 자동 평균 3.666초였으며, 자동 복구 방식이 약 80.8% 짧게 측정됐다.

## 2. 자동 확장의 효과와 한계

HPA는 CPU 사용률에 따라 Pod를 1개에서 2개로 증가시켰고, 부하 종료 이후 다시 감소시켰다.

## 3. 배포 안정성

Readiness Probe 설정 오류를 가진 신규 Pod가 Ready 상태에 도달하지 못했으나, Rolling Update 전략에 따라 기존 정상 Pod가 유지됐다.

이를 통해 잘못된 배포가 진행될 때 Kubernetes가 최소 가용성을 유지하도록 구성할 수 있음을 확인했다.

## 4. 모니터링 및 장애 감지

PrometheusRule이 실험용 Pod의 NotReady 상태를 감지하고 Firing으로 전환되는 것을 확인했다.

이를 통해 Kubernetes 리소스 상태를 기반으로 장애 알림을 구성하고 운영 상태를 관찰할 수 있음을 검증했다.

## 5. 인프라 관리

Terraform으로 EKS 인프라를 구축하고 기존 Metrics Server Add-on을 State에 편입했다.

최종 Plan 결과에서 변경 사항이 없음을 확인하여, 관리 대상 리소스에 대한 코드와 실제 AWS 환경의 상태 일치를 검증했다.

# ▪︎ 회고 및 개선점

## 1. 배운 점

<aside>

### 자동 복구는 장애 유형에 따라 다르게 동작한다

Pod 삭제는 ReplicaSet이 대체 Pod를 생성할 수 있지만, CPU 부하 증가는 HPA가 대응하며, 잘못된 배포는 Probe와 Deployment 전략이 영향을 준다.

따라서 장애 종류와 복구 기능의 관계를 이해하는 것이 중요하다는 점을 확인했다.

### Pod가 복구되는 것과 서비스가 복구되는 것은 다르다

Pod의 Ready 전환 시간만으로 사용자 요청이 정상화됐다고 판단할 수 없다.

실제 서비스 복구를 평가하려면 사용자 요청의 오류율과 응답 회복 시점을 함께 측정해야 한다.

### 자동 확장이 반드시 성능 개선을 보장하지 않는다

HPA가 정상적으로 확장되더라도 기존 연결 방식, 부하 크기, 서비스 병목에 따라 성능 개선이 나타나지 않을 수 있다.

### 장애 감지와 복구를 하나의 흐름으로 이해해야 한다

모니터링으로 장애를 발견하는 것뿐 아니라, 원인을 판단하고 복구하며 정상 상태를 다시 검증하는 과정이 중요하다.
