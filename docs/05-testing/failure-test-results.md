## ▫︎  Pod 수동 복구 vs 자동 복구

| 회차 | 수동 복구 | 자동 복구 |
| --- | --- | --- |
| 1회 | 34.358초 | 4.183초 |
| 2회 | 12.013초 | 4.144초 |
| 3회 | 10.933초 | 2.670초 |
| 평균 | **19.101초** | **3.666초** |

### 분석

- 자동 Pod 복구의 평균 Ready 도달 시간이 수동 방식보다 약 80.8% 짧게 측정됐다.
- ReplicaSet이 새 Pod를 생성하여 원하는 Replica 수를 유지하는 것을 확인했다.
- 수동 실험에는 운영자 개입과 명령 실행 시간이 포함됐다.
- 두 실험의 실행 조건이 완전히 일치하지 않기 때문에 측정 결과를 동일 조건의 서비스 MTTR이라고 해석하지 않는다.

## ▫︎  배포 실패 및 Rollback

| 항목 | 결과 |
| --- | --- |
| 장애 주입 | Readiness Probe 포트 오류 |
| 정상 Pod | 1/1 Ready 유지 |
| 신규 Pod | 0/1 Ready |
| 실패 판정 | ProgressDeadlineExceeded |
| 복구 방식 | kubectl rollout undo |
| 복구 소요 시간 | **16.360초** |

### 분석

잘못된 신규 Deployment가 Ready 상태에 도달하지 못하는 상황에서도 기존 정상 Pod를 유지했다.

수동 Rollback을 통해 정상 Deployment 상태로 복귀했으며, 롤백 실행부터 완료 확인까지 16.360초가 측정됐다.

이 시간은 실제 서비스 중단 시간이 아니라 관리 작업의 완료 시간이다.

## ▫︎  Prometheus 장애 알림

| 항목 | 결과 |
| --- | --- |
| 장애 유발 | 실험 Pod Readiness 실패 |
| Pod 상태 | 0/1 Running |
| Prometheus | Firing 확인 |
| Alertmanager | 알림 그룹 표시 확인 |
| 복구 조치 | 실험용 Pod 삭제 |

### 분석

Kubernetes 리소스의 NotReady 상태를 PrometheusRule을 통해 감지하고 Alertmanager에서 알림을 확인했다.

장애 탐지부터 알림 수신까지의 지연 시간을 별도로 정량화하지는 않았다.
